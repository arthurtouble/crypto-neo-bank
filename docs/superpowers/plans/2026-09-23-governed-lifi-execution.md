# Governed LI.FI Swap Execution Plan

> Execute against the approved [product-parity design](../specs/2026-09-22-aurel-product-parity-design.md) and the [transaction-evidence plan](2026-09-22-transaction-evidence.md). Every stage uses failing tests first and an independent code review. Never enable signing merely because a provider quote contains calldata.

## Goal and invariant

Enable customer-confirmed same-chain Swap and supported cross-network routes only after Aurel binds an exact, current, server-held route to a reviewed intent and independently verifies every prerequisite, source transaction, and destination delivery. Quote discovery, wallet approval, source submission, provider status, and destination receipt are different states. An unindexed hash, LI.FI `DONE` response alone, or an approval log is not a completed Swap.

The first deployment remains read-only. Activation requires action-bound, server-verifiable step-up, audited router/bridge/spender allowlists and ABIs, a controlled beta, independent security review, and operator rollback coverage. Tokenized securities are excluded from generic Swap even if a DEX quotes them.

## Stage 1 — Immutable server-held quote plan

Add a backward-compatible D1 migration for short-lived, subject-scoped plans. The record must include opaque plan ID, authenticated subject and linked wallet, canonical source/destination asset IDs and chain IDs, exact raw input, intended recipient, slippage, minimum output, LI.FI quote/step/tool IDs, approval spender, full normalized unsigned source call (server only), route-policy/catalog versions, observed/expiry times, and a stable fingerprint. Never return calldata as quote metadata or accept browser-supplied expected effects as authority. Mark expired/superseded plans unusable; bound retention and deletion must not remove evidence for a submitted intent.

Refactor the LI.FI adapter to return internal plan plus public `ValidatedSwapQuote` from one parse. Continue supporting decimal and `0x` transaction values with uint256 bounds. A quote containing an unknown target, tool, spender, nested destination call, inconsistent chain/token/amount/recipient, or missing minimum fails closed. Do not treat `allowExchanges` as a universal tool/bridge allowlist: configure and test LI.FI `allowExchanges` versus `allowBridges` separately and compare the returned tool/route against explicit audited policies. Stage 1 persists plans but exposes no signing.

Tests: quote/plan fingerprint determinism, subject/wallet isolation, stale/superseded plan, tampered calldata/recipient/minimum, exact hex/decimal values, unknown tool/bridge/router/spender, and no executable call in the public response. Run migration/recovery, unit, typecheck, lint, and build before review.

## Stage 2 — Review, prerequisite approvals, and simulation

Create a reviewed Swap intent tied to one plan ID and action identity. Preparation accepts only `{intentId, planId}`. Recheck subject, linked wallet, invitation/country/capability, feature and incident switches, screened asset eligibility, fresh independently valued amount and balance, limits/cooling, and quote expiry. Decode the actual route calldata against audited contract and selector policy; a target allowlist without semantic decoding is insufficient. Reject unknown nested calls, permit data, third-party recipient, changed amount, or unmodeled gas/value.

Read token allowance independently. If insufficient, generate a **separate** immutable exact bounded ERC-20 approval to the validated spender; model a zero-reset token as its own step. Each step needs its own current policy, exact-action step-up, simulation, wallet confirmation, hash binding, successful receipt, finality, and matching approval effect. Never generate unlimited approval. Once an approval settles, fetch a fresh quote and revalidate the whole route. Any executable-call fingerprint change (including router or calldata with identical displayed economics), worsened minimum, changed asset, wallet, recipient, tool, spender, or material fee creates a new reviewed plan/intent; expiry always forces requote. Do not transplant fresh calldata into an already approved plan. Simulate and fingerprint the final call just before asking Privy to sign. No browser-supplied call becomes authoritative.

Tests: allowance race, wrong spender/amount, token requiring zero reset, approval cancellation/failure/reorg, quote expiry after approval, changed route/fee/minimum, router/calldata-only change, policy/step-up change, simulation failure, and multi-step replay. Preserve the current fail-closed UI until these tests and an independent review pass.

## Stage 3 — Source and destination evidence

Bind each reported hash to its prepared chain/from/to/value/data and inspect receipt in a canonical block after required finality. Verify route-specific source debit/deposit/bridge effects, not receipt success alone. The existing generic intent reconciler must not mark Swap or bridge intents `confirmed` from source-chain prepared steps alone; add an intent-type-specific terminal gate before the new destination reconciler is connected. The browser status route must not accept a customer-reported terminal `failed` state for a pending Swap, because the transfer may still settle and be retried. Track source submitted, source confirmed, destination pending, completed, partial, refunded, failed, replaced, and reorged distinctly. A replacement may inherit the plan only if its transaction still matches the fingerprint; otherwise stop.

For cross-network routes, query LI.FI `/v1/status` with the bound source hash/tool/chains and verify its sending hash matches. `NOT_FOUND` and `PENDING` stay pending. `DONE/COMPLETED` is corroboration only: require bridge-specific message/transfer identity or a contracted settlement record linking the source deposit to the destination transfer. Also independently observe the bound destination hash, successful receipt and finalized block, and prove the requested wallet received the requested asset and at least the reviewed raw-unit minimum. An unrelated transfer to the wallet cannot close the intent. `DONE/PARTIAL`, `DONE/REFUNDED`, `FAILED`, and `INVALID` must never be labeled exact Swap success. Provider outage, unknown destination hash, and reorg leave an explicit unresolved state; never automatically resend.

Tests: generic reconciler cannot confirm a source-only Swap, browser cannot declare a pending Swap failed, source hash substitution, missing/deceptive logs, unrelated destination transfer, destination to wrong wallet/token/chain, less than minimum, partial/refund, provider 200/NOT_FOUND, RPC outage, replacement and reorg, and idempotent reconciliation after a Worker restart. Provide customer and operator exception views without inventing balances.

## Stage 4 — Activation and experience

Only after stages 1–3 and the separate step-up gate pass, connect the Swap UI to exact preparation, customer wallet confirmation, and evidence status. Present amount and minimum first; show material fee, price impact, approvals, and network path in review. Keep quote search broad but execution limited to legally eligible assets and audited routes. Add keyboard, reduced-motion, desktop/mobile, cancellation, expiry, and partial-settlement checks. Update docs and production smoke. Authorized humans test real transactions in a designated, small-funds beta; automation never signs mainnet money movement. Independent security and legal review, provider/RPC reliability, on-call response, and rollback are required before activation.
