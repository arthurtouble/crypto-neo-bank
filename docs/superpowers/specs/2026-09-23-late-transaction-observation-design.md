# Late Transaction Observation Without New Authorization

Status: design for review. This document does not authorize a new signing route or enable a financial feature.

## Purpose and boundary

A customer-controlled wallet can broadcast an exact prepared transfer before Aurel receives its hash. Today, the first `/api/intents/status` report is rejected if the reviewed window or prepared call has expired, the account is locked, beta access is revoked, or the transfer flag is turned off. A retry works only if the hash was already stored. This conflicts with the product's rule that a previously broadcast transaction must remain observable after a kill switch closes. On-chain settlement and Aurel's in-app authorization are different facts; one must never be inferred from the other. This does not claim control over transactions a customer signs outside Aurel.

The initial scope is an authenticated subject reporting a Base direct-transfer hash against an existing immutable prepared call. It includes legacy and held `awaiting_step_up` calls as **observation candidates only**. No observation response contains executable calldata, changes a feature or account control, renews review, consumes a passkey authorization, or grants a signing permission. Swap, bridge, approval, and DeFi calls stay on their current fail-closed paths until their distinct settlement models are reviewed. “Access revocation” means beta/product eligibility changed while Privy can still authenticate the same subject; an unauthenticated person must use a separately reviewed dual-controlled operator intake, not a public submission endpoint.

## Approaches considered

1. Remove expiry and feature checks from the existing submitted-status path. Smallest code change, but it would conflate a late on-chain observation with an authorized submission and could let the current reconciler mark the intent normally confirmed. Rejected.
2. Keep the candidate only in browser storage until controls reopen. This can lose the only reported hash on device loss and makes a kill switch hide an in-flight transfer. Rejected.
3. Add an observation-only evidence path, then reconcile it independently of approval. Recommended. It adds a narrow D1 table and read model, but preserves the authorization boundary.

## Evidence model

An append-only `intent_observation_candidates` table records a server-generated report ID, subject, intent, step, chain, normalized hash, first report time, immutable prepared-call fingerprint and phase at report time, and the control reason(s) that prevented normal submission. Store only non-sensitive bounded reason codes, not browser explanations. A case-insensitive unique `(chain_id, transaction_hash)` key prevents one candidate hash being attached to two intents. Cross-table triggers also reject a candidate hash already present in ordinary `intent_prepared_calls.reported_hash`, and reject a later ordinary claim of a candidate hash. SQLite serializes these writes so the cross-table check cannot race. Allow at most five candidate hashes per prepared step, enforced by the conditional insert, and rate-limit reports. A duplicate report of the same hash is idempotent; a different hash does not overwrite another candidate or the prepared call's existing `reported_hash`.

Candidate verification has its own monotonic state: `unindexed`, `identity_matched`, `identity_mismatch`, `settled`, `reverted`, or `check_failed`. Store canonical receipt/block evidence, effect result, observation time and last check separately from the initial immutable report. A matching transaction must pass chain ID, hash, from, to, value, and calldata-hash comparison against the immutable prepared call; the existing exact-call and effect verifiers should be reused. A receipt alone is not a completed transfer. Reorgs can downgrade settlement evidence and must preserve the original report. A candidate is never copied into the ordinary `intent_prepared_calls.reported_hash` claim merely to make the existing reconciler pick it up.

The authorization classification is always `approval_unverified_after_control_change` for this path, even if the transaction's economic effect later settles. `settled` means only that the chain confirms the exact effect. It must not change the parent intent to ordinary `confirmed`, satisfy an approval-required schedule, consume membership/rewards eligibility, or imply that Aurel authorized the transfer. If the parent intent was cancelled or failed before the report, retain that state and surface a high-severity exception; never silently rewrite the historical cancellation. Existing normal in-window status reporting and reconciliation remain unchanged.

## Request and reconciliation flow

`POST /api/intents/status` first authenticates the subject, validates the hash, and loads the subject-owned immutable intent and prepared call. A same-hash repeat already accepted through the normal path remains idempotent. If normal submission gates are open, preserve the existing path and its exact-call checks. If one or more gates closed (expiry, beta eligibility, feature switch, account lock, wallet unlink, prior cancellation/failure, or held step-up phase), the route may accept an **observation candidate**, not a submission. A session that is not authenticated as the original subject remains denied. The route must never return an executable call. Use a conditional D1 insert that proves subject/intent/step/fingerprint ownership and enforces the unique hash and per-step cap atomically. Return `202` with an explicit `observationPending` status; never `submitted` or `confirmed` solely from the browser report.

An unindexed hash remains `unindexed`, visible as “Checking transfer” and eligible for bounded, fair retry. Do not reject it only because RPC has not indexed it yet. A background or authenticated reconciliation pass checks the canonical transaction and receipt. If the transaction identity differs, record `identity_mismatch`, open an operational issue, and do not associate it with a settled customer transfer. If it matches, verify finality and the expected native/ERC-20 effect; show `settled`, `reverted`, or `still checking` with an explicit “Aurel approval could not be verified” qualifier. An RPC outage is `check_failed`, never success. Retry order must not starve older candidates or those whose RPC has temporarily failed.

The ordinary status route must still refuse **new preparation and signing** after a control closes. A late observation cannot restart a cancelled intent, reserve funds retroactively, or make a held `awaiting_step_up` call executable. Existing approval/cooling/valuation policy remains authoritative only for normal signing. Candidate reconciliation continues after feature shutdown or beta revocation, subject to read access and operator incident policy.

## Customer and operator views

Activity shows one linked exception item with the transaction hash and a human status: “Checking transfer”, “Transfer settled — approval review needed”, “Transfer reverted”, or “Transfer did not match the reviewed details”. Avoid showing raw D1 phases, risk codes, or an ordinary green success state. A visible link to the chain explorer is acceptable after chain/hash validation. The normal intent remains separately legible but must not duplicate the transfer as an approved completion. Operators see the immutable prepared fingerprint, control snapshot, canonical transaction/receipt evidence, retry history, and issue link. Neither view treats a support response as automatic authorization.

The Activity read response has a separate, subject-scoped `observations` array (latest 50 reports) with report/intent links, chain, hash, report/check times, and one of the human statuses above. It does not expose verification phases or reason codes to the customer. The exception section remains visible independently of ordinary Activity filters and CSV exports; the existing `intents` array and approved completion counts do not absorb these reports. An explorer link is rendered only for a known chain and a valid transaction hash.

## Security and recovery invariants

- Only a fresh authenticated session for the original subject can submit a candidate. A revoked beta entitlement or account lock does not turn that observation into an action permission. An invalid Privy session never bypasses authentication.
- A reported hash is a claim until independent RPC observation. Validate network, canonical identity, receipt finality, and expected economic effect before showing settlement.
- The same hash cannot attach to another subject/intent/step, including across ordinary claims and observation candidates. A single prepared call cannot gain two ordinary completions; conflicting exact-match candidates open an issue for human review.
- Normal submit remains conditional on current authorization. Observation-only evidence cannot be used by any signing or step-up endpoint, reward engine, provider settlement adapter, or eligibility calculation.
- D1 is a projection. Backups retain candidates, verification history, and operator issues; recovery from a missing row may accept a customer resubmission of the same hash. Do not invent a balance or settlement state from the report. There is no automatic evidence purge until counsel approves a retention schedule.
- No production deploy until independent security review verifies route races, SQL constraints, test coverage, operator response, and customer copy. The dev Worker keeps all money-movement flags disabled while this is built.

## Verification and rollout

Write failing route/SQLite tests first for expiry, flag shutdown, beta revocation, lock, wallet unlink, held step-up, unindexed hash, exact match, mismatch, duplicate and conflicting hashes, cancelled intent, the five-candidate cap, and concurrent reports. Test that every case leaves normal signing disabled and that a matching late transaction never becomes an ordinary approved confirmation. Exercise reorg, reverted receipt, RPC failure, and retry fairness against the existing evidence verifier. Extend the isolated D1 backup/restore drill and Activity API/UI tests; run unit, typecheck, lint, app/docs builds, desktop/mobile, and candidate smoke. Use only synthetic transactions and read-only chain checks. The migration must be applied before any Worker that writes the new table. If candidates exist, rollback to a Worker that hides them is not an acceptable normal release path; keep the observation surface available and forward-fix. Counsel and support must sign off on the proposed customer wording before public activation. Keep an operator kill switch for new financial actions without disabling observation.
