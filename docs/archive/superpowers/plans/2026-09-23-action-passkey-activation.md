# Action-Bound Direct-Transfer Activation Plan

This plan is **not** permission to enable a signing route. The verifier, challenge issuer, and one-use authorization store are disconnected foundations. Required step-up transfers still return `step_up_unavailable`; account-policy relaxations remain blocked.

## Current sequencing gap

`/api/intents/prepare` can now persist an exact high-value Base direct-transfer call in `awaiting_step_up` after the current policy, valuation, simulation, and fee checks. Its response does not release the call or return a signing fingerprint; the D1 trigger prevents changing its phase, hash, or verification state. The wallet UI still exits on `requiresStepUp` before calling prepare, and no public passkey or release route exists. The challenge issuer requires an active credential and approved country configuration, so the end-to-end authorization remains unavailable. The post-broadcast status/reconciliation route does not provide pre-sign authority, and browser-side simulation is not server evidence.

## Required order

1. **Fix the exact origin and enrollment policy.** Obtain the approved production HTTPS origin and matching RP ID. The existing exact `*.workers.dev` allowance is for development only. Design first-credential bootstrap, revocation, and account recovery with independent review; a logged-in session alone must not activate a new authorizer. Keep credentials pending until that assurance completes. No customer route before this decision.
2. **Create a two-phase direct-transfer plan.** For a reviewed Base transfer that requires step-up, the server validates linked wallet, current invitation/country/feature/security policy, recipient cooling, fresh externally sourced value, available balance and fees, and the exact native/ERC-20 calldata. It persists a short-lived immutable prepared call in an `awaiting_step_up` state without releasing an executable call to the browser. A D1 migration must preserve old rows and make phase transitions monotonic. No generic swap, bridge, Aave, approval, or arbitrary contract call enters this initial scope.
3. **Simulate the exact call server-side.** Bind RPC chain, canonical block hash, from/to/value/data, expected effect, and simulation time to the prepared fingerprint. Fail closed on RPC error, revert, false token return, stale or changed block, unverified balances, or unknown fee coverage. Re-simulate after material state change and immediately before signing. A simulation is not a settlement guarantee.
4. **Issue and verify one passkey challenge.** The server—not the browser—selects the exact configured origin/RP, authenticated subject/session, prepared intent/step/fingerprint, and current policy version. The challenge issuer stores only the digest. Verify the signed WebAuthn assertion with user verification, then consume it once in the D1 store. An authorization applies to exactly one prepared step and expires no later than the challenge, intent, or call. Recheck wallet ownership, beta/feature/lock, cooled recipient, valuation, and rolling spend at consumption.
5. **Build the final submit gate.** Immediately before the wallet modal, the server atomically checks the unconsumed single-use authorization, prepared call, latest fresh valuation and spending reservation, active policy/version, linked wallet, canonical simulation, and current feature/incident switches. It returns only the exact previously reviewed call. A second submission or a changed fingerprint/session/policy fails. The wallet remains customer-controlled; Aurel can govern only the in-app path unless a separately reviewed wallet signer policy enforces the same rule globally.
6. **Observe effects and recover safely.** Bind any reported hash to the exact prepared from/to/value/data, canonical receipt, required finality, and native/ERC-20 effect. Ambiguous broadcast stays pending; never automatically resend. Reorg, replacement, failure, and incident lock preserve observation without authorizing a new action. Exercise restored D1, expired authorization, retry, and operator recovery.

## Verification and release gates

- Test high-value prepare → challenge → signed assertion → one submit; replay/concurrency; changed call, session, wallet, policy, price, spend, recipient, beta status, and incident switch; stale or inconsistent RPC; ambiguous broadcast and recovery. Keep existing low-value and `step_up_unavailable` tests green until the complete path is reviewed.
- Run unit, typecheck, lint, app/docs builds, isolated D1 recovery, desktop/mobile keyboard and reduced-motion journeys, and a controlled candidate smoke on the exact production domain. Automation never signs a mainnet transaction.
- Independent security review must find no open Critical/High issue. Human operators must approve enrollment/recovery, incident response, production migration ordering (`0024`, `0025`, then any two-phase migration), and a small-funds designated-tester rollout. Counsel and provider approvals remain separate for regulated surfaces.
