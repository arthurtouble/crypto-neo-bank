# Portfolio history operations

Historical portfolio data is a rebuildable projection. Wallets, chains, protocol contracts, and contracted providers remain the sources of asset and settlement truth. `portfolio_*` D1 tables are not a customer ledger. Do not use a cached point to decide whether a payment can be sent.

## Current activation boundary

- Account scope comes from a fresh server-side Privy linked-wallet read. A browser address or a `wallet_references` row cannot add an account to history.
- The current historical indexer adapter is Base-only and requires a configured Blockscout Pro credential, working native, internal, and token-transfer pages, and chain-RPC finality checks. Aave activity is a separate source. If either source is unconfigured, incomplete, or does not match its documented response shape, history remains unavailable.
- Source token precision must be an explicit integer from 0 to 36; null, coercible strings, and omitted decimals cannot become zero-decimal balances. A Base event must have an indexed block hash matching the independently checked RPC block. For ERC-20 transfers, a successful canonical receipt must contain the exact token, participants, raw amount, and log position, while an on-chain historical `decimals()` read must match the indexer. Native top-level transfers now require the exact canonical transaction hash, block, sender, recipient, and raw amount. Only proven transfers expose the opposite address as a counterparty candidate. Internal traces still lack independent call-trace proof: a nonempty internal stream leaves coverage incomplete rather than inventing a native balance effect.
- A native outgoing fee uses canonical receipt execution gas plus Base's L1 data fee and any provable operator fee. [Base's fee specification](https://specs.optimism.io/protocol/isthmus/exec-engine.html) and [Jovian update](https://specs.optimism.io/protocol/jovian/exec-engine.html) show why execution gas alone is not a full debit. The adapter checks raw receipt identity and required fee fields; missing L1 fee or ambiguous nonzero operator parameters leave coverage incomplete. A receipt is an RPC observation, not a consensus proof from a locally run node, so production activation still needs provider-shaped reconciliation and independent review.
- The Aave activity adapter now treats the [paginated activity API](https://aave.com/docs/mcp/tools) as a claim and corroborates each Supply, Withdraw, Borrow, or Repay with the matching [Pool event](https://github.com/aave/aave-v3-core/blob/master/contracts/interfaces/IPool.sol) in a successful, finalized canonical receipt. It checks the governed Pool, event signature, log index, reserve, position owner or beneficiary, raw amount, block hash, and block time. A successful transaction without that exact event leaves the page incomplete. This is an RPC observation, not a locally verified consensus proof. Protocol activity is excluded from liquid wallet quantities and still makes subsequent historical Aave valuation partial: dated supply/debt balances and accrued interest are not yet independently reconstructed, and receipt tokens must not be double counted.
- Current Aave supply and debt now come from `getUserReserveData` for every reserve at one 20-block-confirmed Base block. The reserve calls are batched through Base Multicall3 in one hash-pinned `eth_call`; configuration reads for active reserves use a second pinned batch. Every result must succeed and decode at its expected position or the entire snapshot is incomplete. The read verifies the governed Pool and data provider, checks reserve precision, sums stable and variable debt in underlying units, and rechecks the block after the scan. The displayed observation time is the block time, not the time an API request happened. Failed, stale, incomplete, or unsupported RPC reads return unavailable rather than a zero balance. This is a current snapshot only; it does not close the historical valuation or interest-attribution gap. The default read-only public RPC is an availability dependency, not a contracted production SLA. [Aave data-provider implementation](https://github.com/aave-dao/aave-v3-origin/blob/main/src/contracts/helpers/AaveProtocolDataProvider.sol), [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898), [Multicall3](https://github.com/mds1/multicall3).
- Chain block time, not the indexer timestamp, dates each event. Internal transfer legs must agree on block number, hash, time, log position, asset, amount, and two server-verified owned accounts. Equal-sized transfers in one transaction cannot be paired by amount alone. Same-block basis movement with competing transactions requires canonical transaction order; otherwise the moved basis is review-required.
- Independent daily USD observations currently cover only the explicitly mapped ETH and USDC instruments. Other assets remain unpriced. The price adapter does not assume a USDC peg or carry a prior price forward.
- A wallet, chain, token, or protocol not covered by every required source is a gap. Do not publish a complete-history claim just because a recent page, current balance, or market quote exists.
- The existing modeled performance series must not be shown as historical account performance. The replacement chart reads only complete, dated projections and leaves gaps unconnected.
- Tax lots and disposals are versioned support records. A transfer between owned accounts preserves basis; a disposal with missing consideration, missing acquisition evidence, or incomplete coverage is `review_required` with a null gain. This is not tax advice.

## Historical Aave valuation research gate

The current four-action Aave feed does not establish a dated position balance. A **server-only raw snapshot reader** now locates the last confirmed Base block before the next UTC midnight and proves that its successor crosses the boundary. It resolves the historical Pool and data-provider registrations, checks deployed code, reads every historical reserve through hash-pinned Multicall3 batches, includes supply plus stable and variable debt, and rechecks both boundary blocks afterward. Failed archive state, malformed reserve data, missing contracts, and changed blocks return unavailable, never a zero. Without an explicitly supplied client or HTTPS `AUREL_BASE_ARCHIVE_RPC_URL`, it returns `archive_unconfigured` without calling a public RPC. The reader is not connected to D1, the public API, or the customer chart; it is **not an activated historical valuation adapter**. The complete chart still has gaps. Compare the raw result with a second provider when independent evidence is required. [Base finality](https://docs.base.org/specifications/base-protocol/consensus/derivation), [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898), [archive-node behavior](https://ethereum.org/developers/docs/nodes-and-clients/archive-nodes/).

Read-only probe on 24 September 2026: `base-rpc.publicnode.com` refused Base block 20,000,000 with `pruned history unavailable` and reported an earliest block of 50,000,000. `mainnet.base.org` returned that older block and an Aave `getPool()` call pinned to its hash, but the current-reserve scan on that public endpoint returned unavailable. Neither public endpoint has been accepted as a complete, reliable historical-position source; a bounded archive-RPC backfill and source-shaped reconciliation are still required before publishing Aave-valued days.

Follow-up probe on 24 September: PublicNode also refused a hash-pinned `getPool()` seven days back (`state ... is pruned`). Base's public RPC returned that historical state, but 11 of 15 concurrent per-reserve calls failed. A single hash-pinned Multicall3 `aggregate3` call returned all 15 reserve positions for a non-customer address at the seven-day block, and all six reserves at block 20,000,000 (19 September 2024). This establishes a plausible batching technique, not a production history feed: one public endpoint, one observation address, two historical points, and no independently reconciled prices or wallet event coverage are insufficient to publish dated value or returns. [Viem Multicall documentation](https://viem.sh/docs/contract/multicall), [Multicall3 deployment reference](https://github.com/mds1/multicall3).

The opt-in `AUREL_LIVE_READONLY=1` historical-reader probe also completed against `mainnet.base.org` for 23 September 2026 and, with `AUREL_HISTORICAL_DAY=2024-09-19`, for 19 September 2024. It used the fixed non-customer `0x…dead` address and checked archive registry, code, reserve batch, and block-boundary reads. Both observations were empty positions, so they do not validate nonzero historical supply/debt calculations or a production service level. The normal unit suite mocks the RPC and never makes these calls. An operator can set `AUREL_BASE_ARCHIVE_RPC_URL` to probe a contracted endpoint later.

A separate opt-in sample used [Aave's published Base collector](https://github.com/aave-dao/aave-address-book/blob/main/src/AaveV3Base.sol) for the preceding UTC day. It found nonzero historical supply and reconciled every returned nonzero leg to the corresponding aToken or debt-token `balanceOf` at the **same block hash** via a second public RPC (`base-rpc.publicnode.com`). The first single-endpoint attempt and a batched retry were rate-limited by `mainnet.base.org`; using the second endpoint allowed the check to complete. This is one public account/day, not a qualified archive service, reserve-version matrix, independent price source, or customer-history backfill. Set `AUREL_HISTORICAL_OBSERVATION_ACCOUNT`, `AUREL_EXPECT_NONZERO=1`, and optionally `AUREL_BASE_RECONCILE_RPC_URL` to reproduce or expand the sample.

Before accepting a production archive source, independently reconcile sampled `getUserReserveData` results with each historical aToken and debt token's `balanceOf` and `scaledBalanceOf` and the Pool's normalized reserve indexes. Token balances and indexes are reconciliation evidence; stored reserve indexes alone can miss interest accrued since the last reserve update. Confirm the historical data-provider ABI across upgrades and the presence of stable debt in older reserves. Cover every reserve held or owed by the account, not only the assets in today's price map. [Aave reserve logic](https://github.com/aave-dao/aave-v3-origin/blob/main/src/contracts/protocol/libraries/logic/ReserveLogic.sol), [current Base address book](https://github.com/aave-dao/aave-address-book/blob/main/src/AaveV3Base.sol), [older reserve data type](https://github.com/aave/aave-v3-core/blob/master/contracts/protocol/libraries/types/DataTypes.sol).

These reads could support an end-of-day supply and debt value only when the rest of the wallet, reserve universe, and independent asset prices are complete. They do not by themselves prove daily interest, cash flows, or returns. The four Pool actions omit aToken transfers and liquidation effects, and third-party actions and repayment with aTokens need separate classification. Keep yield and return attribution unavailable until a complete ordered flow record reconciles to the dated balances. Never add valued aToken receipts to their underlying supplied amount. [Aave Pool events](https://github.com/aave-dao/aave-v3-origin/blob/main/src/contracts/interfaces/IPool.sol), [aToken transfer interface](https://github.com/aave-dao/aave-v3-origin/blob/main/src/contracts/interfaces/IAToken.sol).

## Refresh and coverage

`POST /api/portfolio/refresh` ingests one bounded source page for one Privy-linked account and one named source. The client receives an opaque continuation token; the server accepts it only if it matches the stored checkpoint. A full covered-through watermark advances only on an explicit terminal page. A rate limit prevents uncontrolled backfill.

An operations refresh should enumerate the current linked-account set, then advance both required source streams for each account. A failed provider call leaves the previous checkpoint intact. Never infer that an empty page means complete unless the source supplies a terminal continuation state. Monitor failed or repeated cursors, missing native/internal transfer streams, changed block hashes, stale price observations, and unresolved classification.

Derived daily values may be published only after source pages and price observations cover the exact interval. The read API must recheck the current linked-account set and source checkpoints; it must return a null point and reason when a daily result is absent or its evidence no longer passes these checks. A newly linked account needs its own backfill before it can be included in a complete aggregate. An unlinked account must disappear from the next read.

`POST /api/portfolio/materialize` rechecks Privy account scope and publishes the latest 90 completed UTC days. Its bounded replay starts on 2023-01-01, accepts at most four Base accounts and 1,000 raw events, and refuses incomplete checkpoints, a truncated scan, or a publication over the atomic D1 statement budget. The publication marker and derived rows commit in one D1 batch; history and tax reads select the marker's version rather than an uncommitted higher version. A request with unchanged inputs is idempotent. The chart can request 7, 30, or 90 days from that publication. Per-account closing-quantity rows are stored only for the latest 30 days to keep four supported two-asset accounts within the atomic batch; the 90-day values are still calculated from the full historical event replay. Kraken daily closes support this bounded window, but only mapped assets receive observations; other prices and days remain gaps. Inception return remains unavailable rather than extrapolated. This endpoint is rate-limited and does not ingest missing source pages automatically.

## Reorganization response

If the indexer block hash differs from canonical RPC evidence, mark affected raw events `reorged`, rewind the source checkpoint, and delete derived quantities, daily results, lots, and disposals from the affected day forward. Keep prior price observations, durable transaction instructions, customer security settings, consent, and audit records. Replay source pages and recalculate after finality. Do not keep displaying a previously complete point as complete during replay.

## Rebuild and rollback

1. Pause publication of new historical results and preserve the current database backup and incident evidence.
2. Confirm fresh Privy scope and source configuration. Check whether the incident is a missing page, an indexer/schema change, a reorganization, a pricing gap, or a calculation defect.
3. Create a new calculation version when logic changes. Re-ingest immutable source evidence, normalize events, fetch independent prices, and derive quantities and values. Do not overwrite a published complete version with a partial rebuild.
4. Compare account/asset quantities against current chain and Aave observations where comparable. Investigate differences and receipt-token double counts before publication.
5. Publish the new version only when coverage checks pass. Otherwise show `Unavailable` with a reason. Re-enable refresh gradually and monitor error and gap rates.

The isolated recovery drill drops and recreates only analytics tables in a restored local database, then checks that security, consent, and operational evidence remain. It does not prove a live provider backfill or authorize production execution.

**Receipt-proof upgrade:** Existing finalized `portfolio_events` retain their old evidence on an ordinary refresh because the source effect key is immutable. The publisher requires Blockscout `sourceEvidenceVersion: 3` and Aave `sourceEvidenceVersion: 3` with `effectProof: canonical_aave_pool_log`; history and tax-support reads hide any publication containing older rows from either source. Aave v3 verifies canonical block time before deciding whether an indexed row falls outside the requested date window. Migration `0027_aave_timestamp_replay.sql` holds every existing publication, including a history with no Aave events, and removes only rebuildable Aave checkpoints and events. The hold keeps historical reads unavailable during replay without deleting chain checkpoints, security controls, payments, or audit evidence. An account with unproven internal traces, incomplete fee fields, or uncorroborated Aave activity cannot pass this gate. Do not merely increase the source ingestion version: that could count old and new economic legs twice. There is no self-service or automatic production rebuild in this branch.

**Migration `0027` release order:** First block `POST /api/portfolio/refresh` and `POST /api/portfolio/materialize` at the edge for all Worker versions, disable any other portfolio writer, and wait for in-flight writes to drain. Confirm the block with a request and keep it in place during backup, migration, and candidate rollout. Back up and inspect production D1, then apply ordered migrations through `0027`; do not let the old Worker write Aave v2 evidence after this point. Roll out the new Worker completely and verify its version and held-publication behavior before removing the edge block. A rollback to a pre-`0027` Worker is **not** safe after the migration; use a forward fix or keep the writer block in place. Re-page Aave from inception for every linked account under the new Worker, reconcile coverage and current positions, and only then rematerialize. If any step fails, retain the block and hold. Do not assume a canary percentage or application flag protects these endpoints on old Worker versions.

During a chain reorganization, a row already marked `reorged` may be replayed under the same source effect key. Its canonical replay replaces all economic fields, timestamp, counterparty, and evidence together; a still-finalized conflicting row instead invalidates coverage and cannot be overwritten.

## Release requirements

Before enabling complete-history messaging, verify the exact provider response fields and commercial rate limits against the contracted account, backfill a controlled test wallet, exercise multi-page continuation and a simulated reorg, and inspect desktop/mobile gap rendering. No real-money transaction is part of QA. Keep production route activation separate from this read-only analytics work.
